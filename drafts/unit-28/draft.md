# 中间件：DDS 主题、rt/lowcmd，以及行业为什么在“去 ROS 化”

> 状态：初稿 v2（2026-10-08，按 v3 深度门加深）。第 3 部收尾。

一台机器的关节在 500 Hz 上被点名，而它的指令要走一条 TCP/IP 网络。第一反应是：**网络很快，这不算事。** 但把这条链上的每一步摊开——谁在找对方、谁在打包、谁在拷贝、谁在系统调用——你会发现真正的问题从来不是带宽，是**最坏情况**。这一章就把这四件事一件件算给你看。

## 宇树的核心不是 ROS

这是本章唯一必须留下的一句话，因为网上大量教程把它讲反了。

宇树的 `unitree_sdk2` **本身不依赖 ROS**。它的核心是 **CycloneDDS**：一组主题（topic）加一套请求-响应服务 [厂]。ROS 2 支持是**另外提供的一层适配**（官方给 `unitree_ros2`，需要自编 cyclonedds 0.10.2 并设 `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`）[厂]。

**为什么会这样？** 因为 ROS 2 自己就是建立在 DDS 之上的。

```text
你的代码 → ROS 2 API（rclcpp）→ rmw 抽象层 → DDS 中间件 → 网络
你的代码 → unitree_sdk2 → DDS 中间件 → 网络
```

第二行少了一整层。对一台每秒要收发几百帧 35 元素数组的机器，**少一层就少一次序列化、少一次拷贝、少一份不确定性**。

所以“去 ROS 化”不是厂商傲慢，是一条非常朴素的工程判断：**当你的关键路径是确定性的时候，抽象层是要付利息的。**

## 三个厂商，三条路

| 厂商 | 机内通信 | 对外二开接口 | 官方理由（可查到的） |
|---|---|---|---|
| 宇树 | CycloneDDS 主题 + 服务 | ROS 2（Foxy/Humble）+ 原生 SDK | 未说明 [未] |
| 智元 | 自研 **AimRT**（2024-09 开源，官方定位“对标 ROS 2”）；2026-03 又开源基于它的 **灵渠 Link-U OS** | ROS 2 Humble + FastDDS，以及 HTTP JSON RPC | 官方称 AimRT 对标 ROS 2 [查] |
| 银河通用 | **公开文档完全没有 ROS/DDS 层** | GalbotSDK（C++/Python），分高层与低层 | 未说明 [未] |

**三家在这一点上的分歧，是全行业最值得注意的技术信号之一**：它们对“关节怎么控制”高度一致（MCU + FOC + 现场总线，第 1 部与第 27 章），对“大脑用什么模型”也高度一致（第 30 章），唯独在**中间件**上各走一条。

原因是中间件这一层**没有公认正确答案**，而且它直接决定你能不能把延迟压进预算。所以每家都自己写了一遍。**而“自己写一遍”具体写什么，看下一节那四件事就清楚了。**

## 先算清一件事：这根本不是带宽问题

要把“负担”说清楚，先得把它不是什么说清楚。宇树 `unitree_hg` 的 IDL 把所有字段都定死了（本章后面那节会逐条拆开），把类型宽度按 4 字节对齐累加，就能算出一帧到底多大 [算]：

```text
一条 MotorCmd  = uint8 mode(1) + 对齐填充(3) + 5×float32 q/dq/tau/kp/kd(20) + uint32 reserve(4) = 28 B
一帧 LowCmd    = 2×uint8(2) + 填充(2) + 35 × 28(980) + uint32[4] reserve(16) + uint32 crc(4) ≈ 1004 B
一条 MotorState = 1 + 3 + 4×float32(16) + int16[2] temperature(4) + float32 vol(4)
                 + uint32[2] sensor(8) + uint32 motorstate(4) + uint32[4] reserve(16) = 56 B
一帧 LowState   = 35 × 56(1960) + version(8) + tick(4) + 头部(4) + IMU 与 wireless_remote[40] 等 ≈ 2.1 kB
—— 剥掉类型名，两行纯字节累加，任何人拿计算器能复核：
1 + 3 + 20 + 4 = 28 B
2 + 2 + 35 × 28 + 16 + 4 = 1004 B
```

拿官方口径的 500 Hz [厂] 去乘：

```text
下行 1004 B × 500 Hz ≈ 0.50 MB/s    上行 2100 B × 500 Hz ≈ 1.05 MB/s
合计 ≈ 1.55 MB/s = 12.4 Mbps，千兆链路要留给它的是 1.2%        [算]
```

**1.2%。** 所以任何“总线/网卡带宽不够”的说法在这一层都不成立，本书也拒绝这样解释。**这一层的敌人只有一个东西：时间的方差。** 而那 1 kHz 环的预算是多少？1000 µs（第 00 章那张六个时间域的表里 ④ 全身控制那一格的上沿；最快的是 ⑤ 关节伺服，50–1000 µs）；而 500 Hz 是 2000 µs。平均时间当然够——**问题是这 2000 µs 里有四件事的最坏情况没有上界。**

## 关键路径上的四件事

**第一件：发现（discovery）。** DDS 是去中心化的，没有配置中心：一个进程要说、另一个进程要听，两者先在组播上互相公告“我是谁、我发布/订阅哪些主题、什么 QoS”，这一步在 RTPS 协议里叫 SPDP/SEDP [行]。它平时安静，**但在两个时刻不安静**：节点启动的那一下，和一个参与者没了心跳的时候——后者会连带把与它相关的所有端点全部删掉重建。**这就是“建链抖动”：一个后来加入的订阅者，可能在某个 2 ms 的点上突然跑一轮发现。** 而一台人形上同时有低层控制、雷达、相机、灵巧手、遥操作好几个参与者，都在同一个组播域里。

那这又靠什么消掉？靠**静态发现**：预先写死对端清单、跳过自动公告，DDS 的实现普遍支持这种配置 [行]。**宇树有没有这么配、它的 `cyclonedds.xml` 长什么样，官方未公布** [未]。

**第二件：序列化。** DDS 传的是结构体，网线上只有字节。把 1004 个字节按 CDR 规则（每类数据对齐到自身大小的整数倍）逐字段写一遍、收端再读一遍——这个动作**必做、可预算**，因为它没有分支也没有分配。但请注意：一旦你换成 ROS 2，数据要先从 rclcpp 的消息对象过一遍 rmw 再到 DDS，**同一份 1004 字节可能被编两遍。** 这就是本章开头那句“抽象层是要付利息的”的具体含义。

**第三件：拷贝。** 一路走下来，一帧 LowCmd 至少被复制这么多次：你的栈/堆上的结构体 → DDS 序列化缓冲区 → 内核 socket 缓冲区 → 网卡 DMA 环。这是四次，而每一次都是**跨所有权边界的复制**，都可能在页错误、内存碎片、或者内核调度上多花一次上下文切换。**为什么它们的最坏情况没有上界？** 因为堆分配器要走哪条路径由**堆此刻的状态**决定，而不是由你决定：命中空闲块时是一次很短的用户态操作，而需要向内核扩堆或触发缺页时，代价要跳到系统调用与页处理的量级，两者相差两个数量级以上 [行]。1 kHz 环的预算是 1000 µs，它容不下一个“由别人决定”的分支。所以实时系统的标准手法只有一条：**所有内存启动时分配完，运行期只写不再申请。**

**那这四次拷贝能不能省掉？** 能，而且只有一条路：**让两个进程看同一块内存。** 发送方把 1004 字节写进一块双方都映射着的共享内存，翻一个原子标志，接收方直接读——**数据一次也没被复制，内核一次也没被叫起来。** 这就是零拷贝（zero-copy，指“数据不需要在缓冲区之间搬来搬去”，不是“不传数据”）。DDS 这一层确实支持它（CycloneDDS 配 iceoryx，ROS 2 的 loaned message 也是同一件事）[行]。

**但人形用不上它，这就是本章要说清的一处边界。** 共享内存的前提是**两个进程在同一台机器上**。而宇树的运控单元与开发单元是两块板子：官方 H1 文档的板载电脑表里 PC1（运控）的 IP 一栏写着 unaccessable，PC2/PC3（开发）是 `192.168.123.162 / 163` [厂]；官方遥操作仓库把 G1 的 PC2 默认写成 `192.168.123.164` [厂]。**跨板就必须过物理网卡，共享内存帮不上忙。** 所以宇树这条链的真相是：`rt/lowcmd` 走的是**以太网上的 UDP**，它靠**定长数组（无堆分配）+ 单一 SDK（少一层 rmw）+ 固定 IP 网段**去换确定性，而不是靠 loaned message。**宇树没有公布它在这条链上是否启用共享内存、静态发现或具体 QoS** [未]。本书只能说：教科书里最值钱的那一招，在这台机器的物理拓扑下是受限的——而它仍然把这套东西跑在了 500 Hz。

**第四件：系统调用与那个 1500 字节的坑。** 发一个 UDP 包是一次 `sendto()`：用户态陷入内核、socket 锁、协议栈处理、驱动排队。**这是关键路径上唯一一段你完全不能控制的代码**——它跑在内核里，被更高优先级的中断抢占，被网卡的中断合并（interrupt coalescing）策略批处理。而这里还藏着一个可算的坑：一帧 LowState ≈ 2100 B，而标准以太网 MTU 是 1500 B，扣掉 20 B 的 IP 头与 8 B 的 UDP 头，**单个数据报的净载荷上限是 1472 B** [行]：

```text
2100 ÷ 1472 = 1.43 ⇒ 一帧状态要拆成 2 个分片        [算]
```

**分片意味着：丢任意一片，整帧作废。** 而 UDP 不会重传。这就是为什么这一层必须配成 best_effort + 只留最新——**因为“半帧状态”比“没有状态”更危险，而协议层没有给你第三种选择。**（宇树未公布它实际的分片与 QoS 参数 [未]，这一条是本书按 MTU 推的。）

这四件事合起来解释了一句话：**宇树为什么在机内用 DDS 但坚决不让 ROS 层进控制环。**

## UDP 与 TCP：为什么实时环宁可丢包也不要重传

DDS 默认走 UDP。你可能会想：控制指令丢一帧，关节不就抖一下吗，为什么要用“不可靠”的协议？

**因为 TCP 的可靠性是用不确定时延买的。** TCP 丢了包要等重传：它先要根据序号发现空洞，再等一个超时或用重复 ACK 触发快重传，然后重新发。**一次重传的代价至少是往返时间量级，而超时重传定时器（RTO）是毫秒到几百毫秒量级的东西** [行]——在 500 Hz 环里，那是一百个周期。**更糟的是 TCP 有序：一帧里的一个字节丢了，后面所有已经到达的数据都要等着**（这叫队头阻塞）。所以“可靠”在传输层意味着：**这一帧一定到，但不知道什么时候到。** 控制环路要的恰恰相反——**要最新的、不要旧的。**

UDP 的取舍就是把“一定到”换成“到了就是新的”。宇树在 IDL 层把这件事做成了语义：**主题配成 best_effort + 只留最新**（丢弃旧帧不重传）。而它同时留了两道兜底：一是 `LowCmd`/`LowState` 里各带一个 `crc` 字段（第 27 章说过，总线层已经有 CRC16/CRC32，DDS 层再有一个，保护的是两段不同的链路）[厂]；二是官方协议在电机层有一个 `timeout` 位——**一段时间没收到新指令就自动停**（第 42 章的安全设计）[厂]。**丢包不可怕，可怕的是丢了还不知道；这两条一起把“不知道”堵住了。**

**那这条链在什么时候断了？** 当你要传的不是控制帧而是别的东西时。文件、日志、模型权重、标定表——这些不能丢，也不新覆盖旧。**同一个 DDS 域里既跑 500 Hz 的 lowcmd 又跑可靠的服务调用，QoS 就得逐条通道分别配**，而官方从未公布它的分区与 QoS 划分 [未]。这也是第 27 章那个“分层”结论在软件层的重复：**不同时间常数的数据，不该共用同一条确定性预算。**

## 现在把宇树这套接口拆开看

从官方仓库能直接读到消息定义（`unitree_ros2` 里的 `unitree_hg/msg/`，以及 `unitree_sdk2` 生成的 `include/unitree/idl/hg/`）[厂]：

```text
LowCmd.msg   : mode_pr, mode_machine, motor_cmd[35], reserve[4], crc
MotorCmd.msg : mode, q, dq, tau, kp, kd, reserve
LowState.msg : version[2], mode_pr, mode_machine, tick, imu_state, motor_state[35],
               wireless_remote[40], reserve[4], crc
MotorState.msg: mode, q, dq, ddq, tau_est, temperature[2], vol,
                sensor[2], motorstate, reserve[4]
```

**这张表里有六个值得停下来的设计决定。**

**一、35 元素定长数组。** 不是变长。为什么？**变长数组意味着堆分配，堆分配意味着最坏情况延迟不可知。** 定长数组可以在启动时一次性分配完，之后每次收发都是 memcpy 一个已知大小的块。这是实时系统的标准手法，代价是“消息永远按最大机型（35 关节）装”，即使 G1 只有 23 个——**用带宽换确定性。** 上一节的算术把这笔交换量化了：23 个关节的真实载荷是 23 × 28 = 644 B，而线上走的是 35 × 28 = 980 B，多花的 336 B 按 500 Hz 折算是 1.34 Mbps，**千兆链路的 0.13%** [算]。这是一笔极其划算的交易，也是为什么这条消息结构长这样。

**二、`crc` 字段。** 第 27 章说过 RS-485 没有内建错误管理，所以宇树在**总线层**加了 CRC16/CRC32 [厂]。而现在 DDS 层又有一个 crc 字段——**两层都做校验**。为什么？因为 DDS 走的是 UDP（IP 网络），UDP 本身不校验载荷。这两层校验保护的是两段不同的链路。

**三、`reserve[4]` 与 `reserve` 字段。** 保留位。它的存在说明**这套消息格式要向后兼容**：以后要加字段，从 reserve 里拿，老代码不会崩。这是接口设计的成熟做法，也透露了它还在演进。

**四、`wireless_remote[40]`。** 遥控器数据被塞进**同一个状态消息**里，而不是单独一个主题。含义很直白：**在任何时刻，控制器都必须同时知道机体状态和人的输入**——因为急停与接管需要它俩在同一时间戳上对齐。这是一个安全设计，不是偷懒。

**五、`tick`。** 一个单调递增的时间基准字段。第 23 章说过“同步是感知的第一约束”——`tick` 就是这台机器上所有数据的对齐锚点。而它同时也暴露了上层的痛：**如果 DDS 层的发现与拷贝让 tick 的间隔抖动变大，第 23 章那个时间对齐就再也做不准。**

**六、话题命名。** 官方能查到的低层通道是 `rt/lowcmd`（下指令）、`rt/lowstate`（全身状态）、`rt/lf/lowstate`（低频版状态）、`rt/secondary_imu`（躯干第二 IMU）、`rt/arm_sdk`（机械臂通道）[厂]。`rt/` 前缀与 `lf/`（low frequency）的区分本身就是一层设计声明：**同一条网络上要同时跑确定性与非确定性两类流量，所以给它们不同的名字与不同的节奏。**

## 请求-响应那一半：为什么不只用主题

DDS 提供两种通信模式：**主题**（发布/订阅，单向、高频）和**服务**（请求/响应，双向、低频）。

宇树两者都用：

```text
高频、周期性、状态与控制   →  主题（rt/lowstate、rt/lowcmd）
低频、一次性、配置与调用   →  服务（版本读取、参数设置、模式切换、OTA 一类）
```

**这个分工值得说清，因为很多教程把它混成一团。** 判据是：这条数据是“持续更新的最新值”还是“一次问答”？前者用主题（新值覆盖旧值，丢一帧无所谓），后者用服务（必须确认收到）。

**而“丢一帧无所谓”这句话本身就是设计承诺。** 主题的 QoS 通常配成 best_effort + keep_last(1)：不重传、只保留最新。这对控制是对的（旧指令本来就该被新指令覆盖），对文件传输是灾难。**所以 QoS 配置不是性能参数，是语义声明。**

（智元对外的 ROS 2 二开接口官方写明 `ROS_DOMAIN_ID=232`、QoS 为 best_effort / keep_last 10 [查]——**同样是 best_effort，但保留 10 条**。这个差别说明两家对“旧数据还有没有用”的判断不同：宇树要最新，智元允许回看一小段轨迹。这是一个可以写进接口文档的、非常具体的哲学差异。）

## 版本地狱：这一节是给你省时间的

任何一份宇树二开教程都会失效，因为版本约束很硬。把能核实到的写死在这里：

```text
cyclonedds 必须自编 0.10.2，并设 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp   [厂]
消息包分两套：unitree_go（老机型）与 unitree_hg（H1_2/G1 等新机型）      [厂]
ROS 2 支持口径为 Foxy / Humble；Jazzy 是否支持需当场核对                [厂][未]
unitree_rl_gym 依赖 Isaac Gym Preview 4（已 EOL）；rl_lab 用 Isaac Sim 5.1 + Lab 2.3 [厂]
```

**“两套 IDL”这一条最容易伤人**：`unitree_go` 与 `unitree_hg` 的消息**不兼容**，字段名与数组长度都不同。你把为 Go2 写的代码直接搬到 G1 上，编译能过（如果你两套都装了）但运行时什么都不发生。

**而 cyclonedds 版本为什么写死到小数点？** 官方 README 甚至要求“编译 cyclonedds 时终端不能 source ROS 2” [厂]——因为两套 cyclonedds 会在同一条 DDS 域里以不同的 RTPS 行为互相打断，症状是“有时能收到、有时收不到”，而这类 bug 最难查。**这条限制不是洁癖，是同一个组播域里跑了两份协议实现的必然结果。**

**判据很简单：先看你的机型属于哪一代协议。** 而这件事，官方文档里是分开写的，教程里几乎从不提。

## 行业在往哪走

把三条线放在一起看，趋势是清楚的：

**一、留 DDS，弃 ROS 上层。** 宇树核心是裸 DDS；openpi、GR00T 这类模型项目干脆提供**裸 socket / websocket 的策略服务**（机器人只管发观测、收动作）[查]；Figure、Tesla 自研 C++ 栈 [查]。

**二、模型侧与本体侧正在用“网络服务”解耦。** 一个 5–10 Hz 的大脑（第 26 章那条带宽除法）根本不需要 DDS 的发现与 QoS 机器——它需要的是一个 HTTP/WebSocket 端点。**于是“中间件”这个词在人形上正在分裂成两个东西：kHz 级的本体总线，和 Hz 级的模型服务。** 用同一套技术管这两件事，是 ROS 1/2 时代的假设。

**三、主权叙事出现。** 中国行业内开始有“多数国产机器人依赖海外 ROS”的担忧与自研中间件尝试（智元 AimRT / Link-U OS 是公开的一例）[查]。**本书对这一条只作记录，不作判断**——因为它是否成立取决于生态成本，而生态成本目前没有可核实的数。

**而“自研中间件”这条路的真实内容，就是上面那四件事的清单**：把发现改成静态、把序列化改成共享内存里的同一份结构、把系统调用从环里踢出去、把 QoS 语义按通道拆开。智元的 AimRT、银河通用的 GalbotSDK、宇树的裸 sdk2 三条路，**在最坏情况预算这一张表上高度相似**——行业不是在做审美选择，是在同一条 1000 µs 的预算线上各自往回挤。

## 边界：这不等说 ROS 不能实时

这一条必须写清楚，否则本章会被读成“ROS 慢所以别用”，而那是错的。

**ROS 2 本身就是为实时设计过的**：它建立在 DDS 上、可以逐通道改 QoS、支持在 PREEMPT_RT 内核上跑、也支持节点内的 loaned message 零拷贝 [行]。**所以“ROS 不能实时”这句话不成立。** 顺带一条已核实的事实：本书检索过全部官方仓库，宇树**没有**提供 `ros2_control` 那一层硬件接口，给的是 URDF 加自定义消息——拿 ROS 2 接宇树时，那一层要你自己写。

宇树和同行的三家做的不是“ROS 不行”的判断，是一个更窄、也更诚实的判断：**在我这条 1–2 ms 的关键路径上，我要少一层能改我代码路径的抽象。** 少一层不是省 CPU——上一节算过，带宽与 CPU 都够用；**少一层是把“最坏情况由谁决定”这件事收回自己手里。** 当你的 SDK 就是你的产品边界，而 ROS 的版本、发行节奏、构建系统与社区补丁不在你手里时，你就不该把控制环押在上面。

**换句话说：去 ROS 化不是性能优化，是责任划分。** 而这条边界在读者那里的实际用法是：**只做上层（感知、规划、数据采集、遥操作）时，ROS 2 那套工具链的价值远大于它的开销；只有当你真的要往那条 2 ms 的通道里写东西时，本章这四件事才变成你的账单。**

## 从 ROS 2 那边看过来：四样东西的真身

如果你是从 ROS 2 那条路进来的工程师，读完上面几节大概会问一句：
**tf2、nav2、MoveIt 2、`ros2_control` 这四样，在一台人形机器人上对应什么？**
这一节就是那张对照表。它的用处不是教你用 ROS，而是让你已有的直觉
在正确的地方生效、在错误的地方失效。

**tf2 = 一棵随时间变化的刚体树。** 它做的事只有一件：把“在坐标系 A 里、
时刻 t 的一个点”换算成“在坐标系 B 里”，靠的是每条边存一个 4×4 齐次变换，
再沿树做矩阵链乘，跨时间就查缓冲区做插值。
**那它为什么进不了 1 kHz 那条环？** 因为它的成本不在乘法上，在**缓冲区与时间**上：
`/tf` 是按消息速率发布的（典型几十到几百赫兹），一次查询要拿目标时刻去插值，
而插值意味着要等两边的那两条消息都到齐。这件事的抖动来自线程与队列，
不来自数学——正好是第 22 章那六个“偷时间者”里的两个。
而在人形本体内部，这棵树其实是**静态**的：连杆长度写在 URDF 里不会变，
唯一变的量就是那 23 个关节角。所以机内真正需要的不是 tf2，
是“正运动学 + 一次链乘”，输入来自 `rt/lowstate` 的 q/dq——本章前面算过那是 1004 字节 @ 500 Hz。
**结论：tf2 是“跨节点、跨时间、给人看”的那一层，不是“每 1 ms 算一次”的那一层。**

**nav2 = 全局路径 + 局部代价地图 + 一个轨迹跟随器。** 它的隐含假设是
“有一个在平面上连续可导的底盘位姿，和一张 2.5D 栅格”。
**人形为什么常常不用它？** 因为双足的支撑面是**离散的落脚点**，不是连续位姿——
这正是第 17 章那条 ZMP / 捕获点链条要解决的东西：可接受的不是“离障碍多远”，
而是“这一脚踩下去重心投影还在不在支撑多边形里”。
于是行业里那一格常被换成 RL 策略 + 足端轨迹，nav2 退到“给我一张能走的图”。

**MoveIt 2 = 正逆解 + 自碰撞检查 + 采样式规划。** 关键机制在逆解：
手臂自由度一多，同一个末端位姿对应**无穷多组关节角**，
你必须要么在几个解析解里挑一个，要么把它写成一个带约束的二次规划去解——
而 QP 的代价按第 19 章那条 **n³** 增长。
宇树在 `rt/arm_sdk` 里做的事，本质是“你别自己解，我直接给末端位姿指令”，
把这条链收进厂商侧。这是接口选择，不是能力差异。

**`ros2_control` = 把 1 kHz 读写抽象成 `read()` / `write()` 的硬件接口层。**
听起来正好是这条环需要的东西，但它跑在 Linux + ROS executor 上：
调度、序列化、回调组这些第 22 章列出的东西一个都没躲开。
**这就是“留 DDS、弃 ROS 上层”这条行业路线的真实理由**——
不是 ROS 太慢这个口号，而是它把三件有抖动的东西（发现、执行器、内存分配）
放进了一个要求最坏情况有界的地方。

**边界（必须说清）**：宇树、智元、银河通用**是否提供 nav2 或 MoveIt 2 的官方接口**，
本书没有逐家核到一手文档，一律 **[未]**；本节讲的是这四样东西各自的机制与失效位置，
不是任何一家的产品事实。版本口径也要自己核对：Humble 与 Jazzy 之间
`ros2_control` 的硬件接口签名有变化，抄来的代码块经常在这上面翻车。

## 类比，以及它在哪儿破

类比：DDS 像一套邮局系统——你不用认识收件人，只要按格式贴好地址，信就到。ROS 像在这家邮局上再开一层公司行政部。

**这个类比在哪里破，而且破得很有用**：邮局保证“送到”，DDS 默认**不保证**。它的 QoS 可以被配成“尽力送、丢了不补、只留最新”——这在控制语义上是正确的，但它意味着**你的程序必须能处理“上一帧根本没到过”**。

而绝大多数写惯了函数调用的人不会去处理这件事。于是出现一类非常难查的 bug：代码逻辑对、参数对、消息格式对，但因为某一帧在 best_effort 下丢了，控制器拿着 8 毫秒前的状态出了 100 牛米的力。

**所以从 ROS 转裸 DDS 的人，真正要换的不是 API，是“消息可能不存在”这个默认假设。**

---

**一个可检验的说法**：宇树的核心通信层是 CycloneDDS 主题与服务，ROS 2 只是其上的适配层，因此“宇树用 ROS”这个说法在架构上是反的。按官方 IDL 字段宽度与 4 字节对齐累加，一帧 LowCmd ≈ 1004 B、一帧 LowState ≈ 2.1 kB，在官方 500 Hz 口径下合计约 1.55 MB/s，只占千兆以太网约 1.2%——**所以中间件这一层的瓶颈不是带宽，是最坏情况时间**，而它来自四件事：发现（组播公告与端点重建）、序列化（跨 rmw 时同一份数据可能编两遍）、拷贝（用户态→序列化缓冲→内核 socket 缓冲→网卡 DMA，四段）、系统调用与分片（`sendto` 之后那段不受你控制的内核路径；2100 B 超了单个数据报的 1472 B 净载荷，必须拆两片、丢一片即整帧作废）。静态发现、共享内存与定长数组分别去掉这三类方差，而共享内存这一招在跨板的两块 PC 上是受限的。行业在保留 DDS 的同时抛弃 ROS 上层，并把模型侧降格为一个 Hz 级的网络服务——**但这是责任划分，不是“ROS 不能实时”。**

**证据等级**：`unitree_sdk2` 基于 CycloneDDS 且不依赖 ROS、ROS 2 适配需自编 cyclonedds 0.10.2 并设 RMW、编译时不能 source ROS 2、`unitree_go`/`unitree_hg` 两套 IDL、全部消息字段与类型、`rt/lowcmd`/`rt/lowstate`/`rt/lf/lowstate`/`rt/secondary_imu`/`rt/arm_sdk` 话题名、500 Hz 与 `control_dt_ = 0.002` 口径、`timeout` 位、H1 板载电脑 IP 与 PC1 unaccessable 口径 [厂]（可从官方仓库文件与文档中心逐字读到）；G1 的 PC2 默认地址 `192.168.123.164` [厂]（官方 `xr_teleoperate` 仓库）；消息字节数 28/980/1004/56/1960/2100 B、644 B、336 B、0.50 与 1.05 MB/s、12.4 Mbps、1.2%、1.34 Mbps、1.43 与“2 个分片”是 [算]（**按字段类型宽度与 4 字节对齐累加的本书估算，线上真实封装开销、是否共享内存、实际分片与 QoS 全部未公布**）；SPDP/SEDP 发现、CDR 序列化、四段拷贝、堆分配的两条路径、1500 B MTU 与 1472 B 净载荷、UDP/TCP 与 RTO、队头阻塞、ROS 2 的实时选项 [行]；智元 AimRT/Link-U OS、`ROS_DOMAIN_ID=232`、QoS best_effort/keep_last 10、openpi/GR00T 裸服务、Figure/Tesla 自研栈 [查]；银河通用无公开 ROS/DDS 层 [厂]（其“没有文档”这一事实本身可核实）；**宇树从未解释为什么选 DDS、未公布其 QoS 配置、发现模式、是否静态发现、是否共享内存、线程与中断亲和性、Jazzy 支持状态** [未]；“主权叙事”相关表述只作记录。
