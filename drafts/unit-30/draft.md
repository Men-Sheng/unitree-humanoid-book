# VLA 的架构共识：四个部件，三选一，一个所有人都同意的分工

> 状态：初稿 v1（2026-10-08）。

## 一个行业在两年内收敛到了同一张图

2023 年，“机器人 + 大模型”有十几种做法。到 2026 年，公开的系统几乎全部长成同一个形状：

```text
视觉与语言输入
      ↓
① VLM 主干（2B–7B）        ← 负责“看懂场景、理解指令”
      ↓ 语义特征 / 子目标
② 动作专家（80M–1B）          ← 负责“生成动作”
      ↓ 一段动作块（horizon 20–50 步）
③ 动作分块 + 异步双系统        ← 负责“慢想快做”
      ↓
④ 关节层执行（第 12 章那条链）
```

这不是某家厂商的设计，是**全行业独立收敛的结果**。本章要解释的是：为什么收敛到这一张图，以及每个部件为什么长这样。

## 部件一：VLM 主干，为什么是 2B–7B 这个尺寸

公开可查到的主干选择（都是各家自己公布的）：

```text
智元 GO-1        InternVL2.5-2B + MoE（隐动作专家 + 动作专家）
银河通用 GraspVLA  InternLM2-1.8B + 冻结的 DINOv2/SigLIP 视觉编码
银河通用 NavFoM    Qwen2-7B
Physical Intelligence π*0.6   Gemma3-4B + 860M flow 动作专家
宇树 UnifoLM-WLA-1.0          6B 全身协调基座（官方口径）
```

**为什么不是 70B，也不是 100M？** 上下界都是算出来的。

**上界由第 26 章那条带宽算术给。** 权重每翻倍，单步时间下限翻倍。70B × 2 字节 = 140 GB，在 100 GB/s 的端侧模组上是 1.4 秒一步——**1 Hz 都不到，而第 26 章已经说明这台机器的语义节奏需要 5–10 Hz。**

**下界由“先验容量”给。** 第 29 章说过，大模型对机器人的价值是**它在互联网上学到的常识**。常识需要参数装。100M 的模型学不会“纸杯捏用力会瘪”。

于是 2–7B 是这两个约束之间唯一存活的窗口——**而且它是被硬件（端侧内存带宽）卡出来的，不是被算法选出来的。** 这一点值得强调，因为它意味着：**当端侧带宽翻倍（Orin → Thor），主流模型尺寸也会跟着翻倍。** 这条预测是可检验的。

## 部件二：动作专家，为什么必须独立

一个自然的问题是：为什么不直接用 VLM 输出动作？语言模型能输出文本，为什么不能输出关节角？

因为**输出的统计性质完全不同**。

语言是离散的、序列化的、每个 token 有明确词表。关节角是连续的、多维同时的（23 个关节一起）、而且**多峰**（第 29 章）。让自回归语言模型逐 token 吐 23 个浮点数，会得到一个又慢又错的东西。

所以全行业的做法是：**VLM 只出语义，另配一个小网络专门出动作。** 这个小网络叫动作专家（action expert）。

它的规模很有意思：

```text
π*0.6       主干 Gemma3-4B  +  动作专家 860M
SmolVLA     总 450M 一手；主干与专家如何分栏未公布 [未]
Figure Helix S2 = 7B VLM    +  S1 = 80M visuomotor
GE-Act      160M 自回归动作解码器 [查]（原稿曾写 flow-matching，已按一手收回）
```

**动作专家比主干小多少，公开口径只有两家给得起。** Helix 是 7 B ÷ 80 M ≈ **87 倍**——两个数都是 Figure 自己那篇博客的原话：`S2 is built on a 7B-parameter open-source, open-weight VLM`、`S1, an 80M parameter cross-attention encoder-decoder transformer`、`Using just one set of neural network weights (7B for System 2, 80M for System 1)`、`operating at 7-9 Hz for scene understanding`、`continuous robot actions at 200 Hz.` [查]。π\*0.6 是 4 B ÷ 860 M ≈ **4.7 倍**，但这组数**本书没读到原文**（官网对带桌面 UA 的请求返回 429），按图例只能记 [推]。SmolVLA 这一家算不出这个倍数：一手只给总规模 `4.5亿参数`（450 M）与动作头是 Flow-Matching Transformer，主干与专家如何分栏**没有公布** [未]——旧稿拿 100 M ÷ 450 M 当“专家 ÷ 主干”，是把总数当成了主干。所以“动作专家比主干小一到两个数量级”这句通例不成立：**够得着一个数量级以上的只有 Helix 一家**，另一家不到 5 倍；本书按这个事实重写判据——动作专家要小得多，是为了让它能跑在高频（下面讲），但“小多少”目前没有跨厂商的通例可给。

## 图纸上还缺第三方：状态机与行为树

上面把这一层叫“分工”：主干慢、管语义；动作专家快、管高频动作。但**一张真正在跑的架构图里还有第三方**，名字很朴素——有限状态机（FSM：把机器写成若干状态加若干迁移条件，任一时刻只处在一个状态里）与行为树（BT：把任务写成一棵只会向下走的树，叶子是条件与动作，序列节点要求全成、选择节点要求至少一个成，每个 tick 从根重新走一遍）。第 00 章那张六层表给这一行写了 1–10 Hz，本书前 29 章没有挖过它。这一节补三跳：**它为什么必须以某个速率存在、它凭什么能被静态界定、它做不到什么。**

**第一跳，速率：不变量必须由不低于“它被违反的速率”的那一层守着。** 第 26 章算过端侧节奏下限：12 GB 权重 ÷ 100 GB/s ⇒ 一次决策 120 ms；第 16 章算过这台机器的窗口：`τ = √(0.66 / 9.80665) = 0.259 s`，延迟占到 τ 的 39%（约 100 ms）就已经明显伤及稳定。两条一起就是一条不等式：**如果“不许倒”这条不变量交给 VLA 自己去检查，最坏情况下它每 120 ms 才看一眼，而这一个 120 ms 已经是要留预算（100 ms）的 1.2 倍** [算]。把同一条不变量交给 50 Hz 的任务层——官方部署配置 `deploy_real/configs/g1.yaml` 的 `control_dt: 0.02` 就是这个节拍 [厂]——最坏发现延迟 20 ms，剩下约 80 ms 才是真正用来“想清楚之后怎么动”的。**同一台机器、同样的模型，两种分层，差的不是算法好坏，是检查速率与被违反速率的大小关系。** 这正是第 12 章那条级联判据（内环带宽必须是外环的 5–10 倍）朝上再用一遍：**守不变量的那一层，必须比“能把不变量搞坏”的那一层快**；否则它会把下层当成“应该会照做”的假设，而这层假设在第 22 章已经被真机打破过一次。

**第二跳，凭什么可界定：这两样的最坏情形能在纸面上算出来。** 行为树的控制流是自上而下一棵树，一次 tick 的工作量上界 = 根到叶的最大深度 × 单节点最坏耗时；深度是你画图时定下的常数（带 `RepeatN` 这类装饰器时把重复次数乘进去，仍是纸面上算得出的常数）。状态机一次 tick 只查当前状态那一行迁移表。**学出来的策略给不了这个承诺**：它的时延随 token 数、KV 缓存长度、批大小变（第 26、34 章那两笔账），部署前给不出静态上界。工程后果是两种完全不同的验证方式：树与状态机可以**穷举迁移**、可以证明“不存在从正常态一步进入危险态的路径”（模型检查那一套吃的就是这个）；而策略网络只能**统计**地报成功率——第 38 章那条 `0.99^N` 复合衰减正是它的另一面：没有静态上界，就只能把长链切段、每段末尾设人工或显式检查点。**所以这一层不是“更聪明的模型”能替换掉的：它提供的不是智能，是可证明的边界。**

顺带一条维护成本的量级 [行]：n 个状态的 FSM，迁移表上界是 n²，新加一个兜底行为要给每个状态都补一条边；行为树把这件事变成 O(n) 的优先级选择（选择节点从上往下，第一个可用的就执行），代价是**可读性**——树的语义靠图和注释，不靠状态图那样一张完备表。这就是小项目用状态机、跨团队的产品用树的现实原因。

**这条“小”不是审美，是一条被钉死的上界。** 第 26 章那笔带宽账在这里反过来用：**一次前向要把“这一步需要的那部分权重”读一遍**，所以每步耗时下限 = 2P_每步 ÷ 带宽（FP16，2 字节/参数）。**这里的 P 必须是每步都要重读的那部分，不是模型总参数**——带 KV 缓存前缀的流式模型只重算专家那一份（本节下面 π0 那段有一手原话，本书上一版正是把总参数当成了它）。要满足节拍，就得让 K 步挤进一个周期：

```text
参数上限 = 节拍 ÷ 步数 × 带宽 ÷ 2 字节        （带宽取第 26 章的 100 GB/s 那一档）

  50 Hz 一拍（20 ms）、K=10  ⇒ 每步 2 ms   ⇒ P ≤ 100 M
  50 Hz 一拍、K=5            ⇒ 每步 4 ms   ⇒ P ≤ 200 M
  200 Hz 一拍（5 ms）、K=1   ⇒ 每步 5 ms   ⇒ P ≤ 250 M
  200 Hz 一拍、K=10          ⇒ 每步 0.5 ms ⇒ P ≤ 25 M
```

**把 Helix 那两条一手数放进去，它自己就解释了。** S1 是 `80M parameter cross-attention encoder-decoder transformer`，而部署那一节写的是 `S1 executes as a separate real-time process, maintaining the critical 200Hz control loop required for smooth whole upper body action` [查]——**每拍一次前向**是 Figure 自己给的。于是那条带宽式子在这里要倒过来用：不是猜它的步数，而是算它对**硬件**提的最低要求。

```text
一次前向要读完 S1：80 M × 2 B = 160 MB
200 Hz ⇒ 每拍 5 ms
所需最低带宽 = 160 MB ÷ 5 ms = 32 GB/s            [算]
若 S1 是个 10 步迭代采样器 ⇒ 320 GB/s              [算]
```

`Helix's training design enables efficient model parallel deployment on Figure robots, each equipped with dual low-power-consumption embedded GPUs` [查]，芯片型号与带宽原文未给 [未]；而同一页给 S1 的定性是 `a simple transformer-based visuomotor policy`，全篇没有为它配任何迭代采样器 [查]。**32 GB/s 这条下界与“simple”那句话互相印证**：S1 能做到 200 Hz，不是因为那张卡跑得快，而是因为它的**一次**前向就出动作。反过来说，本书上一版在这里写的“5 ms 预算放得下 3 次前向，所以绝不可能塞进十步迭代”是**拿自己假设的 100 GB/s 当厂商事实**——嵌入式 GPU 的带宽一旦不是 100 GB/s，那条“不可能”就同时站不住，而它本来也不该由带宽来判。

**再看 Figure 怎么处理“慢的那一半”。** 原话是 `S2 operates as an asynchronous background process, consuming the latest observation ... It continuously updates a shared memory latent vector that encodes the high-level behavioral intent`，以及 `The asynchronous execution model allows both processes to run at their optimal frequencies` [查]。两条进程之间**没有节拍同步**，靠一个共享隐向量交接。这就把第 31 章那条 `H·Δt` 换成了另一种东西：不是“一次推理管多少拍”，而是“快环允许拿着多旧的语义继续动”——`During training, we add a temporal offset between S1 and S2 inputs. This offset is calibrated to match the gap between S1 and S2's deployed inference latency` [查]，他们连训练时的时序偏移都按部署延迟校准过，为的就是让“旧”这件事在训练里就见过。**这才是双系统的真实接口：一个带时延的共享变量，而不是一条总线上的握手。**

**再拿 π0 自陈的数做一次外部核对——这一次核对把我上一版的推理推翻了，所以把它连错带改一起印出来。** 上一版本节写过一条“三数闭合”：3.3 B × 2 字节 ÷ 3.35 TB/s = 1.97 ms 一步，十步 19.7 ms，正好塞满 50 Hz 的 20 ms 一拍，“用掉 98%”。**那条推理错在三个地方，而三个地方都是我把厂商没说过的话补成了自己的假设。**

**一，那张卡。** 我写的是“它跑在服务器卡上（H100 的 HBM3 约 3.35 TB/s）”。原文是 `The operations were timed on an NVIDIA GeForce RTX 4090 consumer-grade GPU`、表题 `TABLE I: Inference time of our model on a NVIDIA GeForce RTX 4090 GPU` [查]——**是 4090，1008 GB/s** [行]，我把带宽换了 3.3 倍，于是“1.97 ms”本身就是凭一个没读到的硬件算出来的。

**二，权重不是每步都读。** 原文两处说得非常清楚：`To speed up inference (which requires multiple forward passes of the action expert), we downsize the action expert to { width =1024, mlp_dim =4096}, resulting in a parameter count of ~300M` [查]，以及 `each step requires running a forward pass on the tokens corresponding to the noisy actions (the keys and values corresponding to the observation are cached)` [查]。**迭代只重算那 300 M，3 B 的主干作为前缀算一次、KV 缓存住。** 我那把 3.3 B 乘十遍的式子因此用错了对象。

**三，预算不是 20 ms。** 原文：`for all other robots, which run at 50Hz, we run inference every 0.5 seconds (after executing 25 actions)` [查]。50 Hz 是**执行**节拍，不是**推理**节拍；一次推理摊在 25 拍 = 0.5 s 上。

而论文附录 A-D 直接把分栏计时给了出来 [查]（3 路相机，4090）：

| 环节 | 耗时 |
| --- | --- |
| image encoders | 14 ms |
| observation forward pass（主干前缀，只算一次） | 32 ms |
| x10 action forward pass (flow)（十步**合计**） | 27 ms |
| network latency（若机外） | 13 ms |
| **total on-board inference** | **73 ms** |
| **total off-board inference** | **86 ms** |

14 + 32 + 27 = 73，这张表自洽 [算]。现在把两边都摆出来：

```text
按我那条错式子：3.3e9 × 2 B ÷ 1008 GB/s = 6.55 ms 一步 ⇒ 十步 65.5 ms
实测十步合计 27 ms —— 比“每步读全量”的下限还低 2.4 倍 [算]
按真实架构：前缀一次 3.0e9 ⇒ 5.95 ms；十步 × 0.3e9 ⇒ 每步 0.595 ms
            带宽下界合计 11.9 ms，实测 73 ms 是它的 6.1 倍 [算]
预算：0.5 s ⇒ 73 ms 用掉 14.6 %（机外 86 ms 用掉 17.2 %）[算]
```

**“实测落在自己推导的下限之下”这一条，本身就是检查式子的办法**：27 ms < 65.5 ms，说明那十步里读的不是 3.3 B。而正确的下界只有 11.9 ms，说明真实系统离带宽极限还有 6 倍余量——余量被注意力、启动开销和 50 个动作 token 的序列吃掉了。**我上一版把 98% 当成“设计闭合”，其实是把一个错硬件上的错式子的巧合当成了证据。**

改完之后，本章真正要的判据反而更硬，而且这次每一环都有原话：**主干可以大，是因为它要么不必每拍都跑（π0 每 0.5 s 推理一次、Helix 的 S2 干脆是异步后台进程），要么干脆不在控制环里（它的输出只是一个共享隐向量）；动作专家必须小，是因为迭代只重算它——`To speed up inference (which requires multiple forward passes of the action expert)` [查]，厂商自己给出的下调理由就是这个。** “比主干小一到两个数量级”是这条不等式的副产品，不是设计偏好：π0 是 3.0 B ÷ 0.3 B = **10 倍** [查]，Helix 是 7 B ÷ 80 M = **87 倍** [查]，两家的差值正好跨了一个数量级。

**第三跳，它做不到什么。** 一，**它不理解任务**：迁移条件是人写死的谓词，画面里出现一个没被写进谓词的情况，它不会绕开，只会留在原状态或掉进兜底。宇树的协议里有 `mode` 字段与超时回落（第 27、43 章引过这些字段 [厂]），而行业里同类的兜底是阻尼模式（damped）：把关节变成阻尼器 [行]——**那是“摔得软一点”，不是“恢复”**；至于宇树内部到底是一棵状态机、有几层、谁来仲裁，官方从未公布 [未]。二，**它的节拍不能无限提**：树读的是状态估计的输出，而估计器自己的带宽在那一层之下（第 24 章），把 tick 提到 1 kHz 只是把噪声更快地传下去。三，**它跟策略之间必须有一个仲裁协议**：谁能否决谁、否决之后由谁恢复、恢复的判据是什么。这三问本书只能给行业通例（主干出语义、动作专家出高频动作、任务层出许可与超时）[行]，给不了厂商事实。

**这一格为什么值得占一页**：整本书在前面把“从一句指令到一个 MOSFET 的关断”接成了链，而链上“指令怎么变成许可”那一跳一直是空的。补上之后，第 31 章那条 `H·Δt ≥ T_infer` 才有承接者——**块内那 800 ms 里机器不是没人管，是被一棵 50 Hz 的树管着；它管不了新情况，但它管得了那几条不许被违反的东西。**

## 部件三：动作头三选一

动作专家怎么“生成”一段动作？三条路，各有代表：

**一、流匹配（flow matching）/ 扩散（diffusion）**
从噪声出发，迭代若干步把它“推”成动作。代表：π 系、GR00T、GraspVLA、GE-Act **不属于这一类**：一手原文写它是 `a lightweight 160M-parameter autoregressive action decoder`——**autoregressive**（自回归解码器）[查]，把它列在流匹配代表里是原稿的分类错误，就此更正。宇树 org 下**另一族**仓库 `unifolm-wla` 的结构记录里有 `unifolm_wla/model/modules/action_model/flow_matching_head/` 这组目录名 [厂]；**WMA-0 自己的文件清单里没有它**（旧稿把两族混成一族，本轮按 `research/humanoid-stack-specs.md` 的逐仓库清点改正）。两家的官方文字都没确认动作头形式 [未]——本书只在“仓库里有这个文件名”这一层引用它。
优点：分布建模好、动作平滑。缺点：**要迭代多步，每步一次前向**（严格说是每步一次“专家侧”前向：主干那部分作为前缀算一次并缓存 K/V）。扩散可能几十步，流匹配通常 5–10 步。**π0 给出一手实证**：论文原话 `10 integration steps`、`3.3 billion parameters`，动作时域 `H=50`、控制频率 50 Hz [查]（arXiv 2410.24164）。**一条一手能核的样本**：论文《Running VLAs at Real-time Speed》（arXiv 2510.26742，Dexmal 与 StepFun）报 `after the 10 denoising steps`，主干是 `a vision encoder SigLIP with 400M parameters and a large language model Gemma with 2.6B parameters`，两个输入视角下 `achieve a latency of 27.3 ms`、硬件是 `under a single consumer RTX 4090 GPU` [查] ⇒ 每步 27.3 ÷ 10 = 2.73 ms。这个数后面第 29 章要用来对照端侧的带宽账。

**二、自回归离散 token**
把动作量化成词表，用语言模型那套逐 token 生成。代表：π0-FAST、GO-1 的隐动作。
优点：复用语言模型的全部基础设施（训练、量化、KV 缓存）。缺点：序列长、误差会累积。

**三、小型交叉注意力视觉运动网络**
不用生成模型，直接一个 80M 的回归网络，输入是 VLM 的特征 + 本体状态，输出是动作。代表：Figure Helix 的 S1。
优点：**最快**。缺点：分布建模能力弱（多峰任务会掉进均值陷阱，第 29 章）。

**判据**：任务多峰且允许慢 → 流匹配；要复用 LLM 工具链 → token；要 200 Hz 控制 → 小回归网络。

**而这三条经常被组合使用**——这正是下一个部件存在的理由。

## 部件四：异步双系统，因为物理要求它

现在把第 26 章与第 17 章的两个数放在一起：

```text
VLM 主干推理：约 100–200 ms 一次   （带宽决定）
平衡需要的反应：约 10–100 ms 一次   （τ = 0.259 s 决定）
```

**主干比平衡慢。** 所以任何“让 VLM 直接输出关节指令”的架构，物理上就不能工作。

全行业的解法是**双系统 + 异步**：

```text
低频系统（S2 / 语义规划）：5–10 Hz，出“下一步该做什么”
高频系统（S1 / 动作跟随）：50–200 Hz，出“这一毫秒关节该怎么动”
两者并行运行，不互相等待
```

公开口径的实例：

```text
Figure Helix：S2 = 7B VLM，7–9 Hz；S1 = 80M visuomotor，200 Hz，
              完全端侧（Figure Helix：`runs entirely onboard embedded low-power-consumption GPUs`） [查]
π*0.6        ：50 Hz 分块；H100 单卡 5 去噪步 63 ms/块，
              机器人端只执行，推理在 GPU 侧（可 websocket 远程） [推]（官网 429，未读到原文）
GO-2（智元）  ：官方口径为 ACoT-VLA，显式动作推理 + 动作思维链 +
              异步双系统（低频语义规划 / 高频动作跟随）           [推]（只见到媒体转述，智元官方页本轮未逐字读到）
```

**“异步”这个词是关键。** 同步的做法是：想 → 等 → 做 → 想。异步的做法是：**一边做上一块，一边算下一块。** 于是延迟被藏在执行时间里。

这需要一个前提：**动作块要足够长，长到能覆盖一次推理的时间。** 于是有了第 31 章那个绕不开的 trade-off。

## 把四个部件接起来：一次完整的推理

以 GR00T N1.7-3B 的公开规格为例（官方仓库自陈 [查]；**这个名字里的 3 B 是整个检查点的参数，它加载的主干是 `nvidia/Cosmos-Reason2-2B`**，下面这张表按主干与头分别记）：

```text
主干  Cosmos-Reason2-2B（Qwen3-VL 架构）
动作头 flow-matching DiT，16 层
action horizon = 40        ← 一次输出 40 步
状态/动作维度 = 132         ← 全身关节 + 末端位姿都塞进一个向量
动作语义 = 相对末端位姿      ← 输出的是“增量”，不是绝对位姿
部署要求 = 端侧 16 GB 以上（RTX 4090 / Jetson AGX Thor / Orin / DGX Spark）
导出 = ONNX / TensorRT
```

**最后两行是我最想让读者看到的。** 一个能导出 ONNX、能在 16 GB 的嵌入式模组上跑、动作是“相对末端位姿”的 3B 模型——**这就是 2026 年“人形大脑”的实际工程形态**。不是云端千亿参数，是本地三 B、可量化、输出增量。

而“输出相对量”这个决定，与第 21 章 `action_scale = 0.25` 是同一件事：**让策略学“该改多少”而不是“该到哪”**，因为绝对位姿对初始条件与机型差异太敏感。

## 类比，以及它在哪儿破

类比：双系统像人的“深思”与“直觉”——想菜谱时用慢思考，接住掉下来的杯子时不用。

**这个类比在哪里破，而且破在关键处**：人的直觉系统不是“另一个小模型”，它与慢系统**共享同一套感知与记忆**。而机器的 S1 只看得到 S2 喂给它的那点特征。于是当 S2 判断错场景（把“泡沫杯”看成“玻璃杯”），S1 会**用正确的力气去做一个错误的事**——它会以捏玻璃杯的力去捏泡沫杯，而且不会怀疑。

**这就是“上下系统之间没有双向纠错通道”这个架构缺陷的具体表现。** 行业目前的答案是加更多数据，而不是改架构。第 34 章的世界模型（世界模型 = 一个能预测「这么做之后会发生什么」的模型；它的四种用法在第 34 章被拆开），一部分动机就是想给这条链补一个“我能预见我做错的结果”的回路。

---

**一个可检验的说法**：全行业在两年内收敛到“VLM 主干（2–7B）+ 独立动作专家（80M–1B）+ 动作头三选一（流匹配/离散 token/小回归网络）+ 动作分块 + 异步双系统（低频语义 5–10 Hz、高频动作 50–200 Hz）”这一张图；主干尺寸的下界由“先验容量”决定、上界由端侧内存带宽（第 26 章）决定，因此当端侧带宽翻倍时主流尺寸会随之上移；动作专家必须独立且小，是因为它要跑在比主干高 5–40 倍（5–10 Hz 对 50–200 Hz 两个端点之比）的频率上，而“异步”成立的前提是慢的那一半不必每拍都跑——本节的一手取证是两种形式：0.5 s 推理一次、执行 25 拍（π0），以及一个后台进程只留一个共享隐向量给前台（Helix）。上一版把这里写成“19.7 ms 用掉 20 ms 的 98%”，是错硬件、错权重范围、错节拍的三重假设，已按论文自己的 Table I 撤回并改写为 73 ms ÷ 0.5 s = 14.6%。

**证据等级**：各家主干型号、参数、horizon、部署门槛里，已逐字读到原文的记 [查]（Helix、GR00T、GAIA-2、DROID、π0、Cosmos 3 Edge，逐条原文见 `research/other-vendor-firsthand.md`）；π\*0.6 那一组的 63 ms/5 步/50 Hz 是 [推]（官网 429 未读到）。**[厂] 只留给宇树，别家一律不用**；“上界由带宽决定”是第 26 章推导的复用 [算]，但**式子里的 P 必须是每步重读的那部分权重**：π0 的十步只重算 300 M 专家（前缀的 K/V 被缓存、那 300 M 是论文自已写明的“ To speed up inference ”一举动，两处均一手）；该论文 Table I 的 14 + 32 + 27 = 73 ms 与“每 0.5 s 推理一次”也是一手 [查]；于是 32 GB/s、320 GB/s、0.595 ms 一步、下界 11.9 ms、余量 6.1 倍、占预算 14.6%、65.5 ms、2.4 倍、87 倍、10 倍 全部是 [算]；**上一版用 H100 的 3.35 TB/s 与“每步读全量 3.3 B”推出的“19.7 ms 用掉 98%”已整段撤回，撤回理由与反证都印在正文里**；**宇树的动作专家规模、动作头形式、是否分块、是否双系统、部署方式全部未公布** [未]；“卖本体 vs 卖能力”的透明度解释是本书推断。
